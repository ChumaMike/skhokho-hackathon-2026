# Adaptive Operating System — Repository-Grounded Gap Analysis

**Status:** Research only. No code changed while producing this document.
**Companion:** [`docs/plans/2026-09-08-adaptive-operating-system-vision.md`](../plans/2026-09-08-adaptive-operating-system-vision.md) — the target product direction this analysis measures against.
**Method:** Direct reading of `prisma/schema.prisma`, `src/middleware.ts`, `src/lib/tenant/context.ts`, `src/lib/auth/guards.ts`, every `src/app/**` route relevant to the owner/staff/customer journeys, `src/modules/tenant/tenant.service.ts`, `src/components/DashboardNav.tsx`, `src/components/StorefrontView.tsx`, `docs/DESIGN.md`, and the test suite file list. Every finding below cites a real file; nothing here is inferred from the vision document alone.

## A. Current-state architecture

- **Stack:** Next.js 15 App Router, React 19, Prisma 6 against Neon Postgres, `zod` validation, `jose`/`bcryptjs` auth, TypeScript. Single Next.js app, no separate backend service.
- **Tenant model:** One canonical `Business` row per tenant (`prisma/schema.prisma:168`). `businessId` scoping is enforced in application code at each query, not via Postgres RLS for the operational tables — RLS/SECURITY-DEFINER RPCs exist only for the identity core (`Customer`/`Membership`/`Visit`/`Consent`, see the file header comment at `prisma/schema.prisma:1-26` and `prisma/sql/`).
- **Two parallel tenant-resolution paths exist simultaneously, and only one of them is live in production:**
  - **Path-based** (`src/app/store/[slug]/page.tsx`) — resolves a business by URL slug via `getBusinessBySlug` (`src/modules/tenant/tenant.service.ts:163`), no DNS/subdomain requirement. Its own comment states plainly: *"works in any environment... is what /discover links to."* This is the route real customers use today.
  - **Subdomain-based** (`src/middleware.ts` + `src/app/tenant/page.tsx`) — a Node-runtime middleware that resolves `<slug>.<PLATFORM_DOMAIN>` via `resolveHostname` (`src/lib/tenant/context.ts:145`) and rewrites to `/tenant/...` with `x-tenant-*` headers. **`PLATFORM_DOMAIN` defaults to `skhokho.co.za`** (`src/lib/tenant/context.ts:33`) and is never set anywhere in this repo (`grep` for `PLATFORM_DOMAIN` across the codebase finds only the default and its own test asserting that default, `src/lib/tenant/context.test.ts:11`). The actual production domain is `skhokho.sgdataint.co.za` — it does not match `skhokho.co.za` or any subdomain of it, so `resolveHostname` falls through every case to its own documented last-resort (`src/lib/tenant/context.ts:234-247`, *"Anything else falls back to the marketing site, not a hard 404"*) and returns `platform_root`. **Net effect: the subdomain multi-tenant system is inert in the real deployed environment today** — it's reachable only on `*.localhost` in local dev, unless `PLATFORM_DOMAIN` is explicitly set to `sgdataint.co.za` (or a real registered domain) as a Vercel environment variable, which the last verified `vercel env ls` output did not show. Both components (`StorefrontView.tsx`) render identically either way, so nothing is *broken* for a customer — but half of a shipped multi-tenant routing system is currently unreachable.
- **Auth:** Three separate JWT cookie types (`skhokho-staff-token`, `skhokho-user-token`, `skhokho-admin-token`, see `src/lib/auth/guards.ts:47-51`). Owners and staff share one token shape (`payload.isOwner` distinguishes them) — there is no separate "owner" token type (`src/lib/auth/guards.ts:141-148`). Customers authenticate by WhatsApp OTP outside this token system (not yet built — `requirePlatformUser`, `src/lib/auth/guards.ts:175-184`, has no session store yet per its own comment).
- **Permission model:** `BusinessRole.permissions` (JSON, typed as `StaffPermissions`, `src/types/index.ts:46-`) is checked per-action via `requireStaffPermission(permission)` (`src/lib/auth/guards.ts:134-169`) at every mutating server action across customers, orders, appointments, catalog, settings, and domains. **Page rendering (GET) is not permission-scoped** — any authenticated team member can view every dashboard page (`requireOwnerSession` = `requireStaff()`, no permission check, `src/app/dashboard/session.ts:13-20`); only the mutation itself is blocked if the role lacks the permission, and analytics/settings pages special-case this by rendering a "you don't have permission" banner in place of the form (`src/app/dashboard/analytics/page.tsx:22-27`, `src/app/dashboard/settings/page.tsx:23-27`) rather than hiding the nav link.
- **Business categorisation exists in the schema and is unused in the UI.** `BusinessCategory` (`prisma/schema.prisma:44-57`: SALON, FOOD_VENDOR, CAR_WASH, RETAIL_STORE, TUCK_SHOP, MECHANIC, HAIR_BRAIDER, NAIL_TECHNICIAN, EVENTS, CHILDCARE, LAUNDRY, OTHER) is captured at registration and used only for the discovery filter (`src/modules/tenant/tenant.service.ts:257-283`) and storefront metadata label (`categoryLabel`, referenced in `src/components/StorefrontView.tsx:64`). No dashboard page, nav item, or onboarding step branches on it.

## B. Current owner journey

1. `/join` (`src/app/join/page.tsx`) — one form: business name, category (required, no free-text), description (optional textarea, added this session), first/last name, email, WhatsApp, password (with show/hide toggle, added this session).
2. `POST /api/platform/join` (`src/app/api/platform/join/route.ts`) creates an `AppUser` + `Business` + subscription + two `BusinessRole` rows + the owner's own `BusinessStaff` row inside `createBusiness` (`src/modules/tenant/tenant.service.ts:63-157`, wrapped in a 15s-timeout transaction because Neon cold-start round trips were measured at 8-17s live, per the comment at lines 146-156).
3. **Confirmed defect:** the route redirects to `/join?ok=1&slug=...` (line 69) and **sets no session cookie**. `/join`'s success branch (`src/app/join/page.tsx:28-44`) shows only a customer-facing "Open my customer sign-up" link to `/r/[slug]` — there is no "Go to your dashboard" link and no authenticated session. The owner must separately navigate to `/login` and re-enter the same email/password they just typed. This is the exact mechanism the vision document's §4 "Current problem" describes, confirmed from code, not assumed.
4. After manually logging in at `/login` (`POST /api/platform/login`), the owner lands on `/dashboard` (`src/app/dashboard/page.tsx`) with **zero products/services, zero customers, zero orders** — a cold dashboard with only the `PublicationStatus` banner (`src/app/dashboard/PublicationStatus.tsx`) telling them what's missing to publish. There is no guided next step beyond that one checklist item (currently just "add a product or service" — see `getPublishReadiness`, `src/modules/tenant/tenant.service.ts:346-358`).
5. No operating-hours, payment-method, or delivery/collection configuration step exists anywhere in onboarding or in Settings (`src/app/dashboard/settings/page.tsx`) — confirmed by reading the full Settings form (About / Contact / Location / Branding / Domains link only). `Business.operatingHours` (`prisma/schema.prisma:207`) is a schema column with **no UI writer anywhere in the app** (only accepted, unused, by `UpdateBusinessSchema`, `src/modules/tenant/tenant.service.ts:55`).
6. Publishing (`publishBusiness`, `src/modules/tenant/tenant.service.ts:375-392`) is a single button once `getPublishReadiness` is satisfied — no preview-confirmation step, no "what publishing means" explanation screen, no QR code or share sheet after going live (the owner is left on the dashboard with the banner simply changing state).

## C. Current customer journey

1. Arrives at `/store/[slug]` (from `/discover`, a shared link, or WhatsApp) — path-based, works without DNS (`src/app/store/[slug]/page.tsx:29-34`).
2. Sees `StorefrontView` (`src/components/StorefrontView.tsx`): header with logo/category/rating, description, then flat product/service lists.
3. **Confirmed defect (vision §10, directly verified):** every single product and every single service renders its **own independent `<form>`** (`src/components/StorefrontView.tsx:116-140` for products, `:170-192` for services), each with its own phone-number input. There is no shared basket/cart — ordering three items means submitting three separate forms with the phone number re-typed three times. `POST /api/store/order` and `POST /api/store/book` each handle exactly one line item per request.
4. **Confirmed defect (vision §10, directly verified):** the booking form's time input is a raw `<input type="datetime-local" name="startTime" required>` (`src/components/StorefrontView.tsx:182-187`) with **no slot picker, no staff-member choice, and no visible availability** before submission. The server-side capacity/overlap check does exist and is real (`createAppointment`, `src/modules/appointments/appointment.service.ts`, uses a Postgres advisory lock to serialize concurrent bookings for the same service/staff — confirmed via the two concurrency tests in `src/modules/appointments/appointment.test.ts`), so a double-booking is correctly rejected server-side with an error message — but the customer only discovers a slot is full *after* choosing an arbitrary time and submitting, not before.
5. Order/booking confirmation is a query-string banner back on the same storefront page (`sp.ok`/`sp.err` handling, `src/app/store/[slug]/page.tsx:54-58`) reading "Order placed — the business will be in touch" / "Booking requested — the business will confirm." No persistent order-status page, no WhatsApp confirmation.
6. Reviews: a customer reaches the review form via an unguessable link built from the order/appointment id (`Review` model comment, `prisma/schema.prisma:785-791`) — no login required, matching the `/store/pay/[orderId]` trust model.

## D. Current staff journey

1. Logs in separately at `/staff-login` (distinct from owner `/login`), issued via `POST /api/platform/staff-login`.
2. **Confirmed contradiction:** the staff invite form (`src/app/dashboard/staff/page.tsx:100-109`) lets the owner pick a `staffRole` label — Staff / Manager / Cashier / Technician (the `StaffRole` enum, `prisma/schema.prisma:80-86`) — implying different responsibility levels. But `inviteStaff` (`src/modules/staff/staff.service.ts:99-114`) always assigns `roleId: defaultRole?.id`, i.e. the single `isDefault: true` "Staff" `BusinessRole` created once at business creation (`src/modules/tenant/tenant.service.ts:114-128`), **regardless of which `staffRole` label was picked.** Every non-owner team member — whether labeled Manager or Cashier — receives the exact same permission set (`canManageOrders`, `canManageCustomers`, `canProcessPayments`, `canReadBookings`, `canManageBookings`, `canIssueLoyalty` true; everything else false). `StaffRole` (the display label) and `BusinessRole.permissions` (the actual gate) are two disconnected concepts today — the invite UI implies a distinction the permission system does not act on.
3. Once signed in, a staff member sees the **identical 9-item `DashboardNav`** as the owner (`src/components/DashboardNav.tsx:16-31`) — Home, Customers, Orders, Bookings, Catalogue, **Staff**, Assistant, Analytics, Settings — including links to pages a non-owner cannot actually use (Staff management, gated by `requireOwnerOnlySession` → redirects to `/login` if reached without owner status, `src/app/dashboard/session.ts:23-30`) or can view but not act on (Settings/Analytics render a "you don't have permission" banner in place of content rather than being hidden — confirmed above in §A).
4. No merchant-initiated order or appointment creation exists anywhere (`grep "^export" src/app/dashboard/{appointments,orders}/actions.ts` returns only `markAppointmentComplete`/`cancelAppointmentAction` and `markOrderComplete` respectively) — a cashier taking a walk-in order or phone booking has no in-app way to record it; only the customer-facing storefront (`/api/store/order`, `/api/store/book`) can create either.

## E. Confirmed UX/workflow defects

Ranked by how directly they block real onboarding, all confirmed from code in this pass:

1. **No session after registration** (§B.3) — the single highest-friction defect; a new owner's very first action after "Create my business" is an unexplained second login. `src/app/api/platform/join/route.ts:69`, `src/app/join/page.tsx:28-44`.
2. **Booking "needs confirmation" is a dead end.** This session's own new `NeedsAttention` component (`src/app/dashboard/NeedsAttention.tsx`, wired from `src/app/dashboard/page.tsx:107-111`) surfaces `"N bookings need your confirmation"` linking to `/dashboard/appointments`. That page's action buttons are only **"Mark complete"** and **"Cancel"** (`src/app/dashboard/appointments/page.tsx:89-104`, backed by `src/app/dashboard/appointments/actions.ts`'s two exports). **There is no "Confirm" action anywhere in the codebase** — `AppointmentStatus.SCHEDULED → CONFIRMED` (`prisma/schema.prisma:118-125`) has no UI or server action that performs it. A merchant who clicks through from "needs your confirmation" cannot confirm anything. This is the exact contradiction flagged as suspected in the task brief, now fully confirmed with file/line citations.
3. **Order pipeline is binary, not the modeled 6-state flow.** `OrderStatus` is PENDING/CONFIRMED/PROCESSING/READY/COMPLETED/CANCELLED/REFUNDED (`prisma/schema.prisma:88-96`), but `src/app/dashboard/orders/actions.ts` exports only `markOrderComplete` — no transition into CONFIRMED, PROCESSING, or READY exists. The UI (`src/app/dashboard/orders/page.tsx:86-94`) only ever offers "Mark complete" on a PENDING order — every order silently skips CONFIRMED/PROCESSING/READY even though `ORDER_STATUS_LABELS` (added this session, `src/app/dashboard/orders/page.tsx:17-24`) already has plain-English labels for all of them, unused by any action.
4. **`StaffRole` label vs. `BusinessRole` permission mismatch** (§D.2) — an owner configuring their team believes they're setting differentiated access and are not.
5. **Two parallel tenant-resolution systems, one of them inert in production** (§A) — not user-visible today (the fallback is silent and harmless), but a real latent gap: any future work assuming the subdomain/`x-tenant-*` header path is live in production would be building against dead infrastructure until `PLATFORM_DOMAIN` is configured.
6. **Custom domains: intentionally and honestly stubbed**, confirmed still true. `DomainStatus` has ACTIVE (`prisma/schema.prisma:264-270`) but `verifyDomain`'s own test (`src/modules/domains/domain.service.test.ts`, per its title "the stub provider never activates a domain, only PENDING -> VERIFYING") confirms a domain can never reach ACTIVE server-side. The Settings page already links out to a dedicated Domains screen with its own disclosure (shipped last session) rather than pretending to work — the vision document's §18 ask to "hide/gate" this is a prominence decision, not a bug fix; the honesty work is already done.
7. **No merchant-initiated order/booking creation** (§D.4) confirms the vision document's own stated assumption is correct — this is a real product gap, not a bug, and any "Quick action" or "Sell" UI promising it needs new backend actions first (see §I).
8. **`operatingHours` is schema-only** (§B.5) — captured nowhere in onboarding or Settings, despite being accepted by `UpdateBusinessSchema`.
9. **`accentColor` is captured but never rendered.** Settings' Branding section lets an owner pick both `primaryColor` and `accentColor` (`src/app/dashboard/settings/page.tsx:204-232`), but `StorefrontView.tsx` only ever reads `business.primaryColor` (line 45) — `accentColor` has no consumer anywhere in the storefront or dashboard rendering.
10. **Analytics is plan-gated to a bare HTML table.** `src/app/dashboard/analytics/page.tsx:61-93` — a `<table>` of Week/Orders/Revenue/New customers/Bookings, gated behind `subscription.hasAnalytics` which defaults `false` on the FREE plan every new business starts on (`BusinessSubscription` model default, `prisma/schema.prisma:323`). A brand-new merchant who onboards today literally cannot see analytics at all, table or otherwise, until upgraded off FREE.
11. **No dashboard reviews page.** `src/modules/reviews/review.service.ts` exists and is used by the storefront (public display) and by `/dashboard/orders` and `/dashboard/appointments` (the "ask for a review" share-link sections, confirmed present in both pages) — but there is no dedicated `/dashboard/reviews` (or similar) page to browse/moderate all reviews in one place. An owner can only see reviews live on their own public storefront.

## F. Information architecture proposal

The vision document's 5-area nav (Home/Work/Customers/Grow/More, §6) is a genuine simplification from today's flat 9-item `DashboardNav.tsx`, but two things should inform how it's built, not whether:

- **"Work" as a single context-aware slot is a bigger structural change than it looks.** Today Orders and Bookings are fully separate route trees (`src/app/dashboard/orders/`, `src/app/dashboard/appointments/`) with separate services, actions, and page components — there is no shared "Work" abstraction to route into. Collapsing them into one nav slot that shows Orders for a food vendor and Bookings for a salon is a **routing/framing decision** (which existing page a nav item points at, informed by `Business.category`), not a rebuild of either page. A business that does both (many `RETAIL_STORE`/`TUCK_SHOP` categories realistically sell products *and* may offer services) needs a tab or toggle inside "Work," not a forced single choice.
- **Permission-based nav visibility does not exist today and would be new, small, additive work** — `DashboardNav` takes only `current: DashboardSection` (`src/components/DashboardNav.tsx:39`), no session/permission input at all. Passing `StaffPermissions` in and filtering `SECTIONS` accordingly is a contained change, but it is a change, not a relabeling.
- Everything else in §6 (moving Assistant off the nav, folding Settings/Domains/Preview under "More"/"My Store") matches the *already-approved and partially-shipped* Increment 2/3/4 roadmap in the separate `velvety-honking-otter.md` plan (see §N below) — the two documents converge here, not conflict.

## G. Target onboarding journey

The vision document's 7-step onboarding (§4) is achievable without new schema for steps 1-4 and 6-7 (account, business basics, branding, first product/service, preview, publish already have real service functions — `createBusiness`, `uploadCatalogImage`, `getActiveCatalog`, `publishBusiness`). **Step 5 (operations: opening hours, appointment duration/capacity, collection/delivery, payment options) needs new UI against the existing but currently-unused `Business.operatingHours` column** (§B.5) — no new migration required for hours specifically, since the column already exists; a delivery/collection preference and payment-options list would need either new `Business.settings` (JSON, already exists, unused today outside this) keys or, if they need to be queried/filtered on later, small additive columns. This should be scoped precisely before building, not assumed.

The single highest-leverage fix, ahead of the full 7-step wizard, is **G.0 — Step 1's session bug (§E.1)**: making `POST /api/platform/join` set the same session cookie `POST /api/platform/login` sets, then redirecting straight into `/dashboard` (or a setup-checklist landing) instead of the customer-facing `/join?ok=1` success card. This alone removes the exact friction the owner is asking to fix, is a same-file change (`src/app/api/platform/join/route.ts`), and does not require the rest of the 7-step wizard to already exist.

## H. Target daily-operation journey by business category

Achievable today, without new backend logic, by **filtering and reordering already-fetched data**, exactly as this session's own `NeedsAttention`/`QuickActions`/`ComingUp` components already do (`src/app/dashboard/page.tsx`, `src/app/dashboard/NeedsAttention.tsx`, `src/app/dashboard/QuickActions.tsx`, `src/app/dashboard/ComingUp.tsx`) — all built this session from existing service calls (`getLowStockItems`, `listStaff`, `listUpcomingAppointments`, `listOrders`), no new queries. A `BusinessCategory → card-order` config (as the existing `velvety-honking-otter.md` plan's §6 already specifies) is the correct, minimal mechanism — a static lookup table, not a schema change. The one real backend gap specific to *daily operation* (not onboarding) is again **merchant-initiated order/booking creation** (§E.7) — the vision document's Salon/Food quick-action examples ("Booking", "New order") cannot be built as simple links the way "Add a customer" and "Give a stamp" were built this session, because no server action exists yet to point them at.

## I. Backend/data changes genuinely required

Confirmed necessary (not merely convenient) to reach the target vision:

1. **A "confirm appointment" server action** (`AppointmentStatus.SCHEDULED → CONFIRMED`) — closes the confirmed defect in §E.2. Small, additive: one new exported function in `src/app/dashboard/appointments/actions.ts` alongside the existing two, following their exact pattern (`requireStaffPermission("canManageBookings")`, then a Prisma update).
2. **Order pipeline transition actions** (PENDING→CONFIRMED→PROCESSING→READY→COMPLETED, plus CANCELLED) — closes §E.3. Same shape as #1, in `src/app/dashboard/orders/actions.ts`.
3. **Merchant-initiated order/booking creation actions** — genuinely new (not filling in an existing stub): a walk-in order or phone booking recorded by staff, distinct from the customer-facing `/api/store/order`/`/api/store/book` flows (which are membership/phone-driven and assume a customer typed their own number). This needs its own design pass — in particular, how a staff-created order attributes a `Membership` (walk-in customers may not want to give a phone number) — before it's built, not just wired as a copy of the existing actions.
4. **Wire `StaffRole` selection to actually vary `BusinessRole.permissions`**, or remove the choice from the invite form until it does something — closes §E.4. Either build 3-4 real preset roles at business creation (mirroring the Owner/Staff pattern already in `createBusiness`, `src/modules/tenant/tenant.service.ts:92-128`) and pick `roleId` from the selected `staffRole`, or collapse the invite form's role selector to a single implicit "Staff" until per-role permissions are actually differentiated — both are small, but the current state (a selector with no effect) is the one option that should not persist.
5. **Operating-hours / operations UI** against the existing `Business.operatingHours` column (§B.5, §G) — no migration for the column itself; may need small additive `Business.settings` JSON keys or columns for delivery/collection preference and accepted payment methods, to be scoped precisely once the actual onboarding step is designed.
6. **`PLATFORM_DOMAIN` environment variable**, set to the real registered domain, if/when the subdomain tenant-resolution path (§A) is meant to actually activate in production. This is a config/credential task (same shape as the already-known `BLOB_READ_WRITE_TOKEN` and `RESEND_API_KEY` gaps), not a code change — `src/lib/tenant/context.ts` already handles it correctly once the variable is set.
7. **A basket/cart mechanism for the storefront** (§C.3) and **a real slot-picker for bookings** (§C.4) are UI/interaction rewrites of `StorefrontView.tsx` and its two API routes, not new data-model work — `Order`/`OrderItem` already supports multiple line items per order (`prisma/schema.prisma:682-744`); today's one-form-per-product pattern simply never accumulates them client-side before submit.

## J. Changes NOT required

Explicitly confirmed as already correct, sound, or sufficient — do not rebuild:

- **Tenant isolation enforcement.** Every dashboard action reads `session.tenantId` from the verified JWT payload, never from client input, and scopes every query by it — confirmed across customers/orders/appointments/catalog actions and by the dedicated isolation test suite (`src/lib/testing/tenant-isolation.test.ts`, plus the per-module "A cannot read/modify B's X" tests listed in the test file survey below). No proposed UX change in the vision document touches this boundary, and none should.
- **Appointment capacity/overlap enforcement.** Already correct and already tested under concurrency (`src/modules/appointments/appointment.service.ts`'s advisory-lock logic; `src/modules/appointments/appointment.test.ts`'s two concurrent-booking tests). The vision's booking-flow rework (§C.4/§I.7) is a presentation layer on top of this, not a replacement for it.
- **Publish/publication lifecycle policy** (`canBusinessBePublic`/`canBusinessAcceptOrders`/`canBusinessAcceptBookings`, `src/modules/tenant/tenant.service.ts:321-331`) — a single, centralized definition of "public," already correctly gates discovery, storefront lookup, and order/booking writes for non-ACTIVE businesses (confirmed by `src/modules/tenant/publication.test.ts`'s test titles). No change needed to reach the target vision; onboarding/setup changes should call into this, not duplicate its logic.
- **Image upload plumbing.** `uploadCatalogImage()`/`isBlobConfigured()` (`src/lib/blob.ts`) already handle validation, tenant-scoped storage keys, and graceful degradation — confirmed already wired into all four catalog actions and the settings logo field. Blocked only on the `BLOB_READ_WRITE_TOKEN` credential (already known, unrelated to this analysis) — not a code gap.
- **The custom-domain honesty work.** Already shipped and already tested (`src/modules/domains/domain.service.test.ts`) — the vision document's ask (§18) is a *prominence* change (gate behind a plan tier / move out of the ordinary journey), not a fix to anything broken.
- **The loyalty/stamp counter workflow.** `stampMember`/`redeemMember` (`src/app/dashboard/customers/actions.ts`) and the existing `StampCard.tsx` UI already implement the vision document's §12 "give a stamp" flow essentially as specified — `docs/DESIGN.md` independently confirms this was always the platform's signature interaction, not something to design fresh.

## K. Security/POPIA risks

- **No new risk identified from anything in the vision document itself** — every proposed change (nav reshaping, category-aware home, order/appointment status actions, storefront basket) operates within the existing `businessId`-scoped, session-derived tenant boundary described in §J. None of it touches the identity-core tables (`Customer`/`CustomerIdentifier`/`Membership`/`Consent`) or their RLS/RPC layer (`prisma/sql/identity_layer.sql`, referenced in `prisma/schema.prisma:23-25`).
- **Existing, unrelated-to-this-vision risk worth carrying forward:** the guard module's own comment (`src/lib/auth/guards.ts:112-118`) flags that most dashboard *read* paths are not permission-scoped (§A) — a low-permission staff member can view data (e.g., full customer list, full order history) their role wouldn't be allowed to *act* on. This predates the current work and isn't introduced or worsened by anything proposed here, but if the vision's "permissions should alter interface visibility" (§2, Staff member) is implemented, it should close this specific gap rather than only add cosmetic nav hiding on top of it.
- **If merchant-initiated order/booking creation (§I.3) is built**, it must attribute the record to a real, tenant-scoped `Membership` the same way the existing customer-facing flows do (never a raw `Customer.id`, per the hard rule already stated in this repo's `CLAUDE.md`: *"Never expose the global Skhokho ID (customers.id) to a business"*) — a new design point to get right, not an existing gap.
- **If `PLATFORM_DOMAIN` is ever set to activate the subdomain routing path (§I.6)**, `resolveHostname`'s existing ACTIVE-only checks (`src/lib/tenant/context.ts:185`, `:212`) already correctly block PENDING_VERIFICATION/SUSPENDED/DEACTIVATED businesses from resolving — no new risk from turning it on, provided the env var points at the real domain and not a placeholder.

## L. Test strategy

Current suite (`find . -name "*.test.ts"`, 8 files, 82 passing tests per this session's last full run) already covers exactly the boundaries that matter most and should be extended, not replaced:

- `src/lib/testing/tenant-isolation.test.ts` — cross-business isolation, the highest-value existing suite.
- `src/lib/tenant/context.test.ts`, `src/lib/tenant/domain-attacks.test.ts` — hostname resolution and domain hijack scenarios.
- `src/modules/appointments/appointment.test.ts` — concurrency correctness for bookings.
- `src/modules/customers/loyalty.test.ts` — idempotency of stamp/redeem RPCs.
- `src/modules/tenant/publication.test.ts` — publish lifecycle and status-gating.
- `src/modules/domains/domain.service.test.ts`, `src/modules/auth/auth.service.test.ts`.

**New tests genuinely needed as the confirmed defects in §E are fixed**, in priority order matching §N:
1. A test asserting `POST /api/platform/join` results in an authenticated session (once fixed) — currently nothing tests post-registration auth state at all.
2. A test for the new appointment-confirm action mirroring the existing `markAppointmentComplete`/`cancelAppointmentAction` test pattern once it exists.
3. A test for each new order-pipeline transition, plus one asserting **tenant isolation still holds** for each new action (matching the existing "A cannot mark B's order paid or cancel it" pattern already used for the current actions).

## M. Migration strategy

Every schema-touching item identified in §I is additive:

- **None required at all** for §I.1-2 (new server actions, no schema change — `AppointmentStatus`/`OrderStatus` already have every needed enum value).
- **§I.3 (merchant-initiated creation)** needs no new table — `Order`/`Appointment` already support a `staffId`-attributed, `membershipId`-optional-at-creation row; this is new *service/action* code, not new schema.

- **§I.7 (storefront basket/slot-picker)** — zero migration; `OrderItem` already models multiple items per `Order` (`prisma/schema.prisma:724-744`).

**No migration anywhere in this analysis touches `Customer`/`Membership`/`Visit`/`Consent`, `Business`'s core identity columns, or any existing enum's *removal* of a value** — consistent with this repo's own stated constraint that the identity core is fixed and RLS/RPC-managed.
